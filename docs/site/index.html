FlashWAF: Python NAND Flash Translation Layer Simulator

A pure-Python simulator of page-mapped FTLs, out-of-place updates, greedy garbage collection, and write amplification under controlled synthetic workloads.

Overview & Purpose

FlashWAF is an open-source research software platform created to model and study the fundamental dynamics of NAND flash write amplification. Designed for researchers, storage systems engineers, and students, it isolates the algorithmic interaction between page allocation, out-of-place updates, and garbage collection without requiring heavy C++ full-system emulators.

Scientific Scope & Boundary: FlashWAF models logical-to-physical address translation and greedy block reclamation under synthetic full-page overwrite distributions. It does not simulate physical NAND analog timing (program/erase microseconds), multichannel interleaving, dynamic wear leveling pools, crash recovery journals, or hardware bit-error ECC. Findings characterize this simulator and do not predict physical SSD endurance.

How Write Amplification Arises in Page-Mapped FTLs

NAND flash memory requires erasing an entire block of pages before any individual page within that block can be written. To handle frequent random overwrites from host operating systems, modern storage controllers use a Flash Translation Layer (FTL):

  • Out-of-Place Updates: When the host overwrites an existing Logical Block Address (LBA), the FTL writes the updated payload to a newly allocated FREE physical page, updates its internal Logical-to-Physical (L2P) mapping table, and flags the previous physical location as INVALID.
  • Greedy Garbage Collection: When free physical pages deplete below a configured threshold, the simulator selects a victim block with the maximum number of invalid pages (breaking ties with lower historical erase counts).
  • Relocation Overhead: Any remaining VALID pages within the victim block must be copied to free pages elsewhere before the block can be erased.

The resulting Write Amplification Factor (WAF) is measured directly at the physical programming interface:

WAF = (Host Page Writes + GC Relocation Page Writes) / Host Page Writes

Key Insight: Locality Without Data Separation

Because FlashWAF models a simplified single-frontier FTL without hot/cold data separation, cold pages and hot pages intermix in the same physical blocks. When greedy GC reclaims victim blocks, persistent cold pages must be copied forward repeatedly, increasing write amplification compared to uniform traffic.

Python Example

import random
from flash_sim import FlashSimulator

# Initialize flash: 16 erase blocks x 32 pages = 512 physical pages
sim = FlashSimulator(num_blocks=16, pages_per_block=32)

# Write full-page logical payloads
sim.write_logical_page(lba=10, data=b"Payload A" * 450)
assert sim.read_logical_page(lba=10).startswith(b"Payload A")

# Generate 2,000 synthetic random writes across 350 LBAs (70% occupancy)
rng = random.Random(42)
for _ in range(2000):
    sim.write_logical_page(lba=rng.randint(0, 349), data=b"Payload" * 450)

# Check hardware invariants and compute WAF
sim.check_invariants()
waf = (sim.physical_page_writes + sim.gc_page_copies) / sim.physical_page_writes
print(f"Host writes: {sim.physical_page_writes}, GC copies: {sim.gc_page_copies}, WAF: {waf:.3f}")

Scholarly Technical Report

Utilization and Locality in a Prepopulated Greedy Page-Mapped Flash Simulator

Author: Arnav Pandya • Date: October 2026 • Identifier: Technical Report FlashWAF-TR-2026-01

Abstract: We measured page-program amplification in a simplified page-mapped flash translation layer simulator at 40%, 70%, and 85% mapped-page occupancy. Each run prepopulated all active logical addresses, applied 5,000 warm-up updates, and measured the next 5,000 updates. Thirty paired pseudorandom seed blocks covered six occupancy-by-workload conditions, for 180 runs. The paired hot/cold-minus-uniform differences were +0.32987 at 40% occupancy (95% CI [0.32665, 0.33310]), +0.60656 at 70% ([0.60054, 0.61258]), and +0.80465 at 85% ([0.78676, 0.82253]). Results characterize one simulator and synthetic workload design, not physical NAND devices.

Frequently Asked Questions

How does FlashWAF compare to full-system SSD emulators like FEMU or MQSim?

FEMU and MQSim simulate complete NVMe/PCIe hardware stacks, DRAM caches, and multichannel flash packages with nanosecond timing. FlashWAF is a lightweight, pure-Python algorithmic simulator focusing on L2P mapping, out-of-place invalidation, and greedy garbage collection. It runs quickly without C++ compilation or kernel modules, making it accessible for rapid experimentation and pedagogy.

Why does hot/cold temporal locality increase write amplification under greedy GC without data separation?

When an FTL does not physically isolate cold data from hot data, cold pages and hot pages share the same erase blocks. Hot pages invalidate rapidly, but the lingering cold pages remain valid and must be relocated by GC, preventing blocks from achieving full invalidation and causing ongoing copy overhead.

Can I replay real block I/O traces?

Yes. The simulator accepts arbitrary integer LBAs via sim.write_logical_page(lba, data), allowing straightforward streaming from parsed SNIA, FIU, or custom block trace files.
